What it takes to build

The two screens beside this, in terms of the code that has to change.

The menu has no categories today

QUERIES.POS_ITEM_META.SELECT_ALL joins costinfo and pos_food_type only. Nothing in the till's menu payload names a category, so the rail has nothing to group by. One join fixes it — the path already exists in SELECT_CATALOGUE_IDS, which resolves a menu id to its itemdetail and CategoryId.

LEFT JOIN itemdetail idt ON idt.Id = im.ItemDetailId
LEFT JOIN categorydetail cat ON cat.Id = idt.CategoryId
-- add: cat.Id AS CategoryId, cat.Name AS CategoryName

Diet needs no backend change — FoodTypeName and FoodTypeIsVeg already arrive, and the grid already draws a badge from them.

Decisions worth your eye

Category and diet are two controls, not one list
A cashier wants “Pizza, veg only”. One merged row of chips cannot express an AND of two different kinds of thing, and folding Veg in among the categories makes “Veg” look like somewhere dishes live.
Counts react to the other filter
With Veg on, “Pizza 12” would be a lie — it is 10. Each count is computed under every filter except its own, so a category showing 0 is greyed and honest rather than a tap that empties the grid for no visible reason.
Search spans everything, filters narrow it
Typing “paneer” with Beverages selected finds nothing, which is confusing. Two options: search clears the category, or the empty state offers “Search all categories instead”. The prototype does the latter — your call.
Vegan is its own chip, not a kind of Veg
pos_food_type seeds Veg, Vegan and Non-Veg, and Vegan has IsVeg = 1. So “Veg” filtering on IsVeg would sweep vegan dishes in. The chips filter on FoodTypeName, and the food-type master is CRUD-managed — a tenant adding “Jain” gets a chip with no code change.

Settle Bill

Why the dropdown truncated
.fd-tender-row select { flex: 0 0 90px } — 90px fixed. That is what turned “District Settlement” into “District S…” in your screenshot. Radio cards give each mode a full line and a second line for the account it books to.
Split payment must survive
Today each tender row carries its own <select>, and the server writes one paymentbreakup per row. Radios that allow only one mode would quietly remove split settlement, so “+ Split payment” adds a second block with its own visible selector and shows what is left to collect.
Portal tenders sit apart
Zomato, Swiggy and District book to Aggregator Receivable, not the drawer. Listing them beside Cash invites a counter sale being settled to a portal, which makes the cash session short. Own heading, own group.
When it is built
Payment modes go in a role="radiogroup" with real <input type="radio">, so arrow keys move between them and the selection is announced — the drawn ring is styling over a real control, never a replacement. Filter chips are <button aria-pressed>. Both keep the app's existing :focus-visible outline (2px solid #2980b9, 2px offset). Every chip and card clears 44px.
